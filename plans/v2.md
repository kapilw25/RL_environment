# 🔁 Phase 2 v2 plan (after an honest negative v1 baseline)

## 📉 v1 baseline result (500 steps, LoRA r16, 2k problems, batch=auto eval)

POST finished (eval done 5/5, export done). The real, shipped table:

| Benchmark      | base (pre) | GRPO (post) | delta |
|----------------|------------|-------------|-------|
| GSM8K          |   20.4     |    17.3     | -3.1  |
| MMLU           |   45.8     |    45.8     | -0.1  |
| ARC-Challenge  |   33.4     |    33.6     | +0.2  |
| HellaSwag      |   52.4     |    52.5     | +0.0  |
| TruthfulQA     |   33.1     |    33.9     | +0.8  |

## 🧨 Brutally honest read

This run did **NOT** work. Four benchmarks are flat (within noise), and **GSM8K, the main skill we trained on, regressed 3 points**. Net: no improvement, one clear regression. Not a result to dress up.

## 🔍 Likely cause

- **Reward / eval-metric mismatch (main suspect).** GSM8K is scored here on **strict-match** (it wants a specific `#### <answer>` / "the answer is X" format). Our GRPO reward checked *numeric correctness* with its own extractor, so the policy likely drifted its output format away from what lm-eval's strict matcher expects. The model may still be "right" but formatted differently, so strict-match drops. (Pre gsm8k was 20.4 strict vs 31.8 flexible, which shows how format-sensitive the metric is.)
- **No chat template at eval** amplifies it: the instruct model is scored without `--apply_chat_template`, lowering absolute scores and making format drift bite harder.
- **Too shallow to move broad tasks.** 500 steps of a 0.5B on a narrow math+science reward barely touches broad multiple-choice (MMLU/HellaSwag), so those stay flat as expected.

## 🎯 What it means

This is a **legitimate negative baseline**, and honestly it is better as evidence than a fake win. It directly motivates v2. The `replay.html` bar race now shows GSM8K dipping below 100% and the rest at ~100%, which is the truthful picture. Ship v1 as the honest baseline, then run v2.

## 🛠️ v2 changes (prioritized by expected impact)

1. 🥇 **Align the reward to the eval metric.** Make `reward_correct` require the exact answer format lm-eval strict-match expects (emit `#### <number>` for GSM8K, a single letter for MC), so the policy optimizes what is measured. This is the single most important fix.
2. 🥈 **Eval with `--apply_chat_template`** (and `fewshot_as_multiturn`). Higher, fairer absolute scores; keep it identical for pre and post so the delta stays fair.
3. 🥉 **More and more varied data.** `train_n` 2000 to 6000-10000, keep the math + MC mix, consider adding a third verifiable skill so the reward touches more of the 5 benchmarks.
4. **More steps, watched.** `max_steps` 500 to ~1000-1500, but monitor for reward-hacking / overfit (reward saturates early; more steps is not linear gain).
5. **Moderate LoRA rank bump, not max.** r16 to r32 (alpha 64). Higher rank adds instability and reward-hacking risk for little gain on a narrow reward; do not maximize.
6. **10 checkpoints + small evals for a real learning curve.** Save 10 checkpoints during training; run `LIMIT=100` evals (all 5 task types) per checkpoint to draw a Phase-1-style climbing curve. Keep one final FULL eval for the headline numbers.
7. **Optional: vLLM for rollout speed** (in a fresh venv, since it pins torch) and/or a **bigger base (1.5B)** to raise the ceiling. Both cost more; add only if v2 with the fixes above still underdelivers.

## ✅ Success criteria for v2

- **No regression on GSM8K** (post >= pre), and ideally a clear positive delta on GSM8K + ARC (the aligned skills).
- Net non-negative across all 5; MMLU/HellaSwag/TruthfulQA at least flat (transfer is a bonus, not required).
- Report the outcome honestly whether it lifts or not. A second honest negative still teaches (reward design is the hard part in RLVR).
